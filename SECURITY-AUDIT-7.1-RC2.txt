A1. class-pclzip.php:3984 — fclose() atas variabel tak terdefinisi
--------------------------------------------------------------------------------
  Kode : fclose($v_file);   // $v_file tidak pernah di-assign di fungsi ini
         (fungsi privExtractFileUsingTempFile, baris 3977-4052)
  Efek : Di PHP 8+, fclose(null) melempar TypeError FATAL (bukan warning).
         @ suppression TIDAK menolongnya (uji: @fclose($undef) tetap TypeError).
  BUKTI: Direproduksi di Chrome headless. Stack trace berakhir di baris 3984.
         Pemicu: PCLZIP_TEMPORARY_DIR tidak writable + entri > threshold
         (memory_limit x 0.47, di-set otomatis oleh privOptionDefaultThreshold).
  KOREKSI PENTING: Baris 2747 (bug serupa) TAK TERJANGKAU — privWriteFileHeader
         selalu return 1. Dan jalur ini TIDAK dicapai WordPress core: core
         memakai extract(PCLZIP_OPT_EXTRACT_AS_STRING) -> privExtractFileAsString
         (nol rujukan temp-file). Hanya terjangkau lewat PclZip::extract() ke
         DISK, mis. plugin pihak ketiga.
  DAMPAK: Rendah. Availability, bukan keamanan. Tidak dapat dipicu penyerang.
  PARITAS: Byte-identik 7.0.3.

A2. wp-admin/includes/export.php — export_wp() mencemari namespace global
--------------------------------------------------------------------------------
  Kode : export_wp() mendeklarasikan 13 fungsi BERNAMA di dalam badan fungsinya:
         wxr_cdata, wxr_site_url, wxr_cat_name, wxr_category_description,
         wxr_tag_name, wxr_tag_description, wxr_term_name, wxr_term_description,
         wxr_term_meta, wxr_authors_list, wxr_nav_menu_terms, wxr_post_taxonomy,
         wxr_filter_postmeta
  Efek : (1) Panggilan KEDUA export_wp() dalam 1 proses -> Fatal "Cannot
             redeclare function wxr_cdata()".
         (2) Plugin yang sudah mendefinisikan salah satu nama itu -> ekspor
             FATAL di panggilan PERTAMA (layar putih di Tools > Export).
         (3) 13 fungsi bocor ke scope global setelah 1 ekspor.
  BUKTI: Direproduksi. `function wxr_cdata(){}` sebelum export_wp() -> Fatal.
         function_exists('wxr_cdata') false->true setelah ekspor.
  DAMPAK: Rendah-Medium. Availability fitur ekspor. Tidak dapat dipicu jarak
         jauh (butuh plugin bernama sama). LEBIH plausibel dari A1.
  PARITAS: Byte-identik 7.0.3.
  CATATAN: PHPStan melaporkan ini (48x "Function wxr_cdata not found", 15x
         "Inner named functions"). Saya sempat SALAH menggugurkannya sebagai
         keterbatasan analisis; ternyata bug runtime nyata.

B1. wp-includes/comment.php:2424 — preg_replace(null)
--------------------------------------------------------------------------------
  Kode : $commentdata['comment_author_IP'] =
             preg_replace('/[^0-9a-fA-F:., ]/', '', $commentdata['comment_author_IP']);
  Efek : Memanggil wp_new_comment() TANPA comment_author_IP -> $subject null ->

  BUKTI: Direproduksi (komentar tetap terbuat, tapi dgn notice).
  DOKUMENTASI vs KODE: docblock baris 2137 bilang "Default empty" untuk

  PARITAS: Byte-identik 7.0.3 (baris 2366 di sana).

[C] RACE CONDITION BY-DESIGN (identik semua versi, dampak rendah)

C1. wp_insert_user — TOCTOU duplikat username
--------------------------------------------------------------------------------
  FAKTA 1 (TERBUKTI): wp_users TIDAK punya UNIQUE constraint pada user_login.
         Skema (schema.php:204): "KEY user_login_key (user_login)" = non-unik.
         Uji langsung: dua INSERT user_login identik -> KEDUANYA sukses, 2 baris
         tersimpan. DB tidak menolak. Identik dgn MySQL (skema sama).
  FAKTA 2 (TERBUKTI, baca kode): user.php:2325
         if (!$update && username_exists($user_login)) return WP_Error(...);
         ... lalu INSERT.  = check-then-act tanpa penguncian.
  KESIMPULAN: FAKTA 1 + FAKTA 2 = TOCTOU secara definisi. Dua registrasi
         konkuren nama sama bisa lolos check bersamaan -> duplikat username.
  BATAS PENGUJIAN (JUJUR): Race menyala saat runtime TIDAK dapat saya
         demonstrasikan di environment ini. Alasan:
           - MySQL sungguhan tak bisa dipasang: Docker Hub, apt Ubuntu, pypi,
             npm, golang-proxy SEMUA diblokir (403). Hanya git-clone jalan.
           - SQLite (drop-in uji) menserialkan tulis -> window tak muncul.
           - Startup proses PHP (~300ms) melebihi window; proses stagger.
           - Drop-in mencegat `new wpdb()` -> tak bisa 2 koneksi terpisah.
         Ini keterbatasan LINGKUNGAN, BUKAN bukti race tidak ada.
  DAMPAK: Rendah. get_user_by('login') pakai LIMIT 1 (baris pertama menang) ->
         isu integritas data, bukan privilege escalation. Penyerang hanya bisa
         "balapan dgn dirinya" (nama existing tertangkap check yg sudah commit).
  KONTRAS (kenapa ini by-design): add_option (option.php:1142) memakai
         "INSERT ... ON DUPLICATE KEY UPDATE" atas UNIQUE option_name = upsert
         ATOMIK. WordPress TAHU cara benar; memilih tidak untuk user karena
         duplikat ditoleransi. Keputusan sadar, bukan kelalaian.
  PARITAS: Skema identik 7.0.3 dan semua versi.

C2. spawn_cron — TOCTOU double-execution cron
--------------------------------------------------------------------------------
  Kode : cron.php:915  $lock = get_transient('doing_cron');   // cek
         cron.php:943  set_transient('doing_cron', ...);       // tulis
         Transient tidak atomik -> window antara cek dan tulis.
  MITIGASI: compare-after-set. wp-cron.php membaca ulang token $doing_wp_cron
         dan hanya proses yang menang lock yang lanjut. Best-effort.
  DAMPAK: Rendah. Worst case satu cron job jalan dua kali. WP sengaja tidak
         pakai DB locking di sini.
  PARITAS: identik semua versi.

CATATAN kelas race: TIDAK ADA pola "SET x = x + 1" (increment SQL non-atomik)
  di seluruh core (grep kosong). Semua counter (comment_count, term count)
  pakai recount SELECT COUNT(*) lalu UPDATE = N -> IDEMPOTEN, aman dari race.

[D] SSRF TEORETIS — DNS-rebinding TOCTOU
================================================================================
  Konteks: pingback.ping (class-wp-xmlrpc-server.php:7072) dan oEmbed proxy
         memakai wp_safe_remote_get (tervalidasi wp_http_validate_url).
  PERTAHANAN (terbukti, uji langsung):
    - Blocklist komprehensif: 127/8, 10/8, 172.16/12, 192.168/16, 169.254/16
      (link-local + CLOUD METADATA), CGNAT, TEST-NET, multicast, reserved.
      Uji: 169.254.169.254, 10.0.0.1, [::1], 0177.0.0.1 (oktal),
      2130706433 (desimal) -> SEMUA DIBLOKIR. Bypass encoding gagal.
    - Revalidasi redirect TIAP HOP: class-wp-http.php:353 daftar
      validate_redirects sbg hook requests.before_redirect; throw bila gagal.
    - Pengecualian loopback HANYA untuk host situs sendiri (uji: dgn
      home=example.com, 127.0.0.1 & localhost DIBLOKIR).
  CELAH TERSISA: DNS rebinding. wp_http_validate_url resolve via gethostbyname
         sekali; fetch resolve ULANG. Penyerang dgn DNS TTL sangat rendah bisa
         balas IP publik ke validasi, IP internal ke fetch.
  DAMPAK: Rendah. Keterbatasan FUNDAMENTAL validasi-resolusi-sekali (bukan bug
         7.1). Butuh DNS terkontrol penyerang. Tak bisa ditambal tanpa pin-IP
         yang tak dilakukan transport PHP mana pun.
  CATATAN: Blocklist 169.254 dari commit 7.1 c794a2e "HTTP API: Improve
         compliance with IPv4 Special-Purpose Address Space" = hardening aktif.
